## 分析

先来分析 arceos/labs/lab1/src/main.rs

alloc_pass不断地在被执行。一次alloc_pass做了什么？

生成一个`Vec<Vec<u8>>`，内层的各个`Vec<u8>`的长度分别是 32 + delta, 64 + delta, ... , 512*1024 + delta。一轮alloc_pass生成一个内含15个`Vec<u8>`的`Vec<Vec<u8>>`items，各个`Vec<u8>`长度不同。

然后free_pass会把items里偶数下标位置的`Vec<u8>`移出来，并检查一下首尾的u8值对不对，于是现在items里只剩7个`Vec<u8>`。

检查通过之后，每轮生成的item里的`Vec<u8>`会被合并到`pool: Vec<Vec<u8>>`里面，也就是说，pool.len()每轮增长7。

现在的目标是，实现内存分配器LabByteAllocator以使pool能增长最多的轮。

首先，arceos/labs/lab1/src/main.rs 涉及到的内存分配有什么？

pool是个栈上的对象，其内部的ptr指向堆上的一段连续内存`[Vec<_>]`，而每个`Vec<_>`内部的ptr又指向堆上的一段连续内存`[u8]`。

## [u8]

容易想到的是，把最后不会被释放的[u8]从一侧开始分配，会被释放的从另外一侧开始相向分配 (相向双指针)。这样不会被释放的就全连在一起，这样就不会有碎片了。

但是可以以一种比较hack的方式来实现[u8]的分配，每轮生成的items的值全是相等的，最后free_pass的检查也比较粗略。那么，干嘛不让各个[u8]共用成最长的那一段呢。

具体来说，直接提前准备`512 * 1024 + max(delta)`长度的内存，`let a = vec![c; base+delta];`触发分配时每次都直接返回给它那段内存的开始地址，vec自己会去赋值成全是c，于是后面free_pass的检查也会通过。一次alloc_pass内部，各个[u8]段复用为了最长的那一段，而由于 arceos/labs/lab1/src/main.rs 不会回过头来检查，下一轮 alloc_pass 可以接着用。也就是说，pool的各个`Vec<u8>`，其内部的ptr全指向同一片内存区域，虽然到最后u8的值已经不对了，但检查的时候是对的。

[u8]的分配，GLOBAL_ALLOCATOR接收到的请求，要求的align为1。

## [Vec<_>]
LabByteAllocator还需服务的一种内存分配是多个连续的struct Vec的分配，这种align为8，而[u8]的分配align为1，可以辨别出来。

pool增长的过程中，[Vec]的长度也在不断变化，此外items也是`Vec<Vec<u8>>`，其也需要分配[Vec]。这部分直接用现成的TlsfByteAllocator来实现。

## 如何划分[u8]和[Vec]使用的动态内存区域
可用的动态内存区域为 [0xffffffc08026e000, 0xffffffc088000000)。

[u8]我们直接准备一段最长的，剩下的部分给TlsfByteAllocator实现align为8的分配。[u8]最长的一段是512*1024 + delta，delta是轮数会增长。

[u8]区域分配多了，TlsfByteAllocator很快就内存用尽了，轮数都还没到，浪费了。[u8]区域分配少了，TlsfByteAllocator能执行多轮，但是512*1024 + delta越过free memory区域了。

先试分配给[u8]共用体 512 * 1024 * 2 字节，这样delta最多能运行 512 * 1024 = 524288 次，实际运行`Indicator: 112735`时TlsfByteAllocator内存就用尽了。改成分配 512 * 1024 + 112735 字节，增加了TlsfByteAllocator的轮数，理所当然的[u8]越界了。然后改成 512 * 1024 + 150000，跑出来`Indicator: 113222`。应该还能微调，不过就这样吧。

## LabByteAllocator的init()与add_memory()
见arceos/modules/axalloc/src/lib.rs GlobalAllocator.init()和alloc()，GlobalAllocator由 一个ByteAllocator 和 一个PageAllocator 组成，一开始只给了 ByteAllocator 32KB，不够了balloc.alloc()会返回Err，再由 PageAllocator 加页给它。

但是这里LabByteAllocator没管init和add_memory，直接认为整个free memory区域[0xffffffc08026e000, 0xffffffc088000000)已经给自己了，total_bytes()也是直接返回 0xffffffc088000000 - 0xffffffc08026e000 = 131670016。

LabByteAllocator.alloc()内存不够返回Err之后，GlobalAllocator.alloc()里打印old_size和expand_size分别会是131670016和134217728，当然self.alloc_pages()分配不了这么大，于是panic Bumb: NoMemory，最后的panic是这样发生的。

## 迷惑点（已解决）
```Rust
println!("size of Vec: {}", size_of::<Vec<u8>>()); // 24
println!("align of Vec: {}", align_of::<Vec<u8>>()); // 8

println!("size of Vec: {}", size_of::<Vec<Vec<u8>>>()); // 24
println!("align of Vec: {}", align_of::<Vec<Vec<u8>>>()); // 8
```

Vec的align应该是为8没错，arceos/labs/lab1/src/main.rs 里改成 `for i in 0..500`，这种情况pool.len()就已经能达到3000多了，然后LabByteAllocator.alloc()里`ax_println!("LabByteAllocator.alloc() size: {} align: {}", size, align);`，输出里align为8的，size最大也才384。为什么？

[群友](https://github.com/mingzi47)帮忙破案了，align为8的，size其实是有大于384的。低估了打印条目的数量级，改成`for i in 0..500`之后，输出的条目还是太多，终端里size > 384的输出被后面的挤掉了（pool扩容导致重新申请分配频率相对低，所以容易被下面的输出挤掉），所以一搜才全是size: 96 192 384这样。打印条件改成：
```Rust
if align == 8 && size > 384 {
    ax_println!("LabByteAllocator.alloc() align == 8 && size > 384: size: {} align: {}", size, align);
}
```
就能看到`LabByteAllocator.alloc() align == 8 && size > 384: size: 86016 align: 8`的输出了。
